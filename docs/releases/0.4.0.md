# triton-msl 0.4.0

[Project](https://github.com/bledden/triton-msl) · [Usage](https://github.com/bledden/triton-msl/blob/main/docs/USAGE.md) · [Changelog](https://github.com/bledden/triton-msl/blob/main/CHANGELOG.md)

0.4.0 is a compatibility and safety update. It runs on the Xcode 27 toolchain,
which the published 0.3.0 refuses, and fixes defects found in 0.3.0. It adds an
export command for external Metal drivers and a per-user start-up identity record.
No general speedup is claimed. This guide summarizes what changes for users and
where limitations remain. The project is alpha.

See [GitHub releases](https://github.com/bledden/triton-msl/releases) for published
artifacts and their hashes.

## What is new

- **Start-up identity record:** a later Python process can reuse a validated
  per-user record of the compiler, SDK and framework identities instead of
  recomputing them from full file bytes. See [Start-up identity record](#start-up-identity-record).
- **Source-program export:** the installed `triton-msl-export` command (also
  `python -m triton_msl.tools.export_source_program`) writes the Metal source, an
  optional metallib and a manifest for a proved saved-LSE attention program. An
  external Metal driver can then run it. The 128-thread cooperative lowering is
  opt-in with `--cooperative`. The external caller owns bounds, geometry, lifetimes
  and synchronization; see [`docs/TRIFAST_EXTERNAL.md`](https://github.com/bledden/triton-msl/blob/main/docs/TRIFAST_EXTERNAL.md).
- **Triangle-attention backward kernels:** the reporter's backward kernels with
  derived contiguous strides and boolean masks now lower on the default path.
- **More than 31 arguments on the host-copy route:** kernels with a compiler-certified
  packed argument layout now run there. 0.3.0 refused them on that route.
- **Dense transposes:** full-storage, zero-offset, dense rank-two fp16/fp32
  transposes take the direct MPS route. Offset, partial, overlapping and gappy
  transposes keep the host route.
- **Default-off experiments:** seven dense attention fragment compositions behind
  `MetalOptions(experimental_fa_fragment_lowering=...)`, plus
  `experimental_cooperative_attention`, `experimental_tiled_k_layout`,
  `TRITON_MSL_HOST_EXTENT=1` and, on the opt-in C++ route,
  `TRITON_MSL_CPP_SCALAR_CFG=1`. None is enabled by default or qualified for
  performance.

## What is fixed

- **Xcode 27:** 0.3.0 refuses every kernel with
  `cannot establish Metal compiler/SDK identity: unsupported native load command 0x27`.
  0.4.0 accepts the `LC_DYLD_ENVIRONMENT` load command, only in a main executable
  and only for `DYLD_VERSIONED_FRAMEWORK_PATH`.
- **Metal language-standard probe (issue #12):** the probe now requires compute
  pipeline creation, not only a library load. If pipeline creation fails for a
  standard, it tries the next older one.
- **Opt-in C++ route:** a masked load could read outside its allocation on inactive
  lanes, and the typed-pointer rewrite dropped `volatile` on loads. Both are
  repaired. The route stays unaudited and off by default.
- **Host-copy route after a failed launch:** 0.3.0 could drop its references to a
  launch's buffers while GPU work was still pending. 0.4.0 keeps them until the
  GPU's access has provably ended and refuses new host launches until then.
- **Resource handling:** pooled buffer leases are released when launch preparation
  raises, and loaded pipelines are released after their loader's matching unload.
- **Identity and subprocess safety:** compiler and probe subprocesses no longer run
  in the application's working directory. Framework discovery no longer risks a
  stale memo after the import machinery is replaced.
- **Installed disassembler:** the `applegpu` decoder is vendored, so disassembly
  works from an installed wheel.
- **Python 3.10:** two cleanup paths added during 0.4.0 development used Python
  3.11 APIs. They now work on 3.10 as declared. This was checked statically and by
  unit tests on Python 3.14; Python 3.10 itself was not run.

None of these fixes corrects a silently wrong result on 0.3.0's default path.
That describes the fixes made; 0.3.0 was not audited again.
Support is source-, dtype- and layout-specific. See the
[capability register](https://github.com/bledden/triton-msl/blob/main/docs/CAPABILITY_AND_REFUSAL_CENSUS.md).

## Performance

Measurements use one M4 Max. Native and pure-Python installations have separate
results.

**Against 0.3.0.** The 0.4.0 release build has not been timed against 0.3.0: not
yet measured for this release. An October 18 comparison timed an October 11
installed development build against released 0.3.0. It resolved none of its 36
cases (18 workloads, native and pure) as faster or slower. That comparison used an
older retained Metal compiler, because 0.3.0 cannot compile with the current one.
A separate October check found the 15 operator kernel sources it covered
byte-identical between 0.3.0 and that development build. No GPU-timestamp
comparison with 0.3.0 exists.

**Against 0.2.0.** The per-launch host cost that 0.3.0 added over 0.2.0 remains in
0.4.0. The records attribute it to the launch identity and descriptor checks
introduced in 0.3.0. In the same October comparison, 10 of 36 cases were resolved as slower than
0.2.0 and the rest were unresolved. On small single-launch workloads the paired
excess was about 18–24 µs for the native wheel and about 45–54 µs for the pure
wheel. The 0.4.0 host fast paths did not measurably recover it: in a November 9
nine-case comparison with earlier development wheels, the native wheel's mean call
time was higher in all nine cases (+1.47% to +10.07%) and the pure wheel was mixed
(−8.14% to +13.23%), with two workers per arm.

**Dense transposes.** Four transposed-B matmul cases fell from 1.08–1.26 ms to
0.21–0.26 ms per public call plus sync, against November 3 development wheels, in
both installed modes. This was not compared with 0.3.0 and is not a release
performance qualification.

**Start-up.** In November 9 runs of a development build without the identity
record, the first add in a fresh process with empty kernel caches took 9.7 to
14.0 s (two observations per arm). The 0.3.0 guide records 9.48 s against 0.63 s
for 0.2.0.

On November 14 the identity record was timed from local builds of the release
source. Each sample is a new Python process that imports torch, triton and
triton-msl and makes one `@triton.jit` vector add on MPS tensors. The table gives
the median time of that first call, then of the whole process.

| Later process | Record off (`TRITON_MSL_IDENTITY_RECORD=0`) | Record in use |
|---|---|---|
| Native wheel, compiled kernels cached (24 processes each) | 7.03 s, 7.88 s | 0.96 s, 1.79 s |
| Native wheel, empty kernel caches (12 each) | 7.32 s, 8.21 s | 1.15 s, 2.03 s |
| Pure wheel, compiled kernels cached (24 each) | 7.06 s, 7.93 s | 0.93 s, 1.74 s |
| Pure wheel, empty kernel caches (12 each) | 7.41 s, 8.24 s | 1.13 s, 1.96 s |

The record does not apply to the first process, which has no record, does the
full computation and writes one. Its first call took 8.64 s with the native wheel
and 7.73 s with the pure wheel. With the record switched off, the first call of
the first process took 14.82 s (native) and 8.23 s (pure). These four are single
observations and their order matters: the 14.82 s call was made by the first
process of the whole schedule. The toolchain files were already in the operating system's file cache and the machine
was doing other work. Other machines, other workloads
and a cold file cache were not measured, and these runs were not compared with
0.3.0 or 0.2.0.

**Attention.** The 0.3.0 comparisons against PyTorch SDPA and MLX were not rerun
for 0.4.0. See the [0.3.0 guide](https://github.com/bledden/triton-msl/blob/main/docs/releases/0.3.0.md#flashattention).

## Start-up identity record

In 0.3.0, every new Python process recomputed the compiler, SDK and framework
identities from full file bytes before its first kernel. 0.4.0 keeps that full
computation for the first process, whenever anything it checks has changed, and on
request. Otherwise a later process validates a small per-user record and reuses the
recorded identity. The record holds the identity the full computation
produced, so cache keys are the same in both modes unless a change listed
below goes unseen.

- The default is on. `TRITON_MSL_IDENTITY_RECORD=0` forces the full computation in
  every process and reads or writes no record. `TRITON_MSL_IDENTITY_RECORD=refresh`
  recomputes and rewrites the record.
- Records live in `~/.cache/triton_msl/identity-v1-uid<uid>/` unless
  `TRITON_MSL_IDENTITY_DIR` is set. The directory is mode 0700 and the files 0600.
- `python -m triton_msl.tools.identity status|refresh|clear|verify` manages the
  records. `verify` runs the full computation and compares. `refresh` and `verify`
  reach the framework record of the command's own process only; for an application,
  use `clear` or run it once with `TRITON_MSL_IDENTITY_RECORD=refresh`.
- The record is used only where file metadata is on APFS and the record folder
  carries no access control list. Otherwise the full computation runs.

The record relies on file metadata, so it does not see what only the full
computation sees: a byte change that leaves a file's size, times and inode
unchanged (for example a write through a memory mapping held open across the
change); a change to an SDK file other than the SDK's version files; a privileged
change to file times or to the raw device; and a record altered by the same user.
If your setup can change in these ways, set `TRITON_MSL_IDENTITY_RECORD=0`.
Details are in
[`docs/CACHE_CONTRACTS.md`](https://github.com/bledden/triton-msl/blob/main/docs/CACHE_CONTRACTS.md).

## Important limits and options

- **Hardware and applications:** testing used one M4 Max. M1 testing remains
  best-effort. The reported full AlphaFold/trifast application has not been
  validated end-to-end.
- **Source-program kernels:** a kernel whose arguments are seven pointers followed by
  four scalars, and that uses `tt.dot` with `exp2`, `log` or `maxnumf`, enters the
  source-program proof by default. The regular Python launcher refuses a proved
  program with `MetalNonRecoverableError`; a failed proof refuses at compilation.
  Export is the supported use.
- **Observation callbacks:** as in 0.3.0, the native fast path checks unchanged
  state without replaying Python observation callbacks. Set
  `TRITON_MSL_IDENTITY_FAST_PATH=0` if your application relies on them.
- **Host extent borrowing:** `TRITON_MSL_HOST_EXTENT=1` can expose allocator-private
  bytes past a tensor's length to the kernel. Correct, bounded kernels do not touch
  them. See [`docs/USAGE.md`](https://github.com/bledden/triton-msl/blob/main/docs/USAGE.md#experimental-host-storage-extent-borrowing).
- **Half accumulation:** `TRITON_MSL_FA_HALF_ACCUM=1` stays opt-in. Its historical
  speed and error figures are not validated.
- **Optional C++ route:** off by default and unaudited.

See the [full limitations](https://github.com/bledden/triton-msl/blob/main/docs/RELEASE_CANDIDATE_LIMITATIONS.md)
for the 0.3.0 validation record that still describes most behaviour.

## Upgrade notes

- **Xcode 27:** no action needed.
- **Identity record:** on by default. The first process, and any process after
  something the record checks has changed, still runs the full computation.
  `TRITON_MSL_IDENTITY_RECORD=0` restores the 0.3.0 behaviour of a full computation
  in every process.
- **`PostSubmitError` after a failed host launch:** if submission or waiting fails
  on the host-copy route, later host launches raise
  `triton_msl.errors.PostSubmitError` until the failed launch's completion is
  proven. It subclasses `RuntimeError`. Retry once completion can be established,
  or restart the worker. `triton_msl.backend._host_dispatch.reap_completed()`
  returns the number of unresolved failed launches. See
  [Host dispatch failures with uncertain completion](https://github.com/bledden/triton-msl/blob/main/docs/USAGE.md#host-dispatch-failures-with-uncertain-completion).
- **New environment variables:** `TRITON_MSL_IDENTITY_RECORD`,
  `TRITON_MSL_IDENTITY_DIR`, `TRITON_MSL_HOST_EXTENT` and
  `TRITON_MSL_CPP_SCALAR_CFG`. Only the identity record is on by default.
- **New compiler options:** `experimental_fa_fragment_lowering` (default `"off"`),
  `experimental_cooperative_attention`, `experimental_tiled_k_layout` and
  `experimental_source_program_cooperative` (each default `False`).
- **Licence metadata:** the package licence expression is now
  `MIT AND BSD-3-Clause` because the wheel includes the BSD-3-Clause `applegpu`
  decoder.

## If you need to roll back

Prefer recreating your earlier lockfile environment. A pin to
`triton-msl==0.3.0` restores the 0.3.0 defects listed above, and on Xcode 27 it
refuses every kernel. Restart the interpreter and verify the imported path and
version after any change. A full downgrade workflow has not been tested.
